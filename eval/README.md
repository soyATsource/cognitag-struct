# 返答の採点

辞書や規則を変えたときに、**返答が良くなったのか悪くなったのか**を判定するための道具です。

```bash
cd D:\AIModel
python -X utf8 cognitag_struct/eval/run_eval.py
```

```
ケース  126/129   97.7%
既知の弱点    0/  8 解消  （点数には含めない）

観点別
  modality              43/ 45   95.6%
  no_question           18/ 18  100.0%
  parsed                16/ 17   94.1%
  policy                17/ 17  100.0%
  policy_prefix          6/  6  100.0%
  question_contains      6/  6  100.0%
  tags_all              50/ 52   96.2%
  text_contains          8/  9   88.9%
  text_none              4/  4  100.0%
```

結果は `baseline.json` に保存されます。次に走らせるときは前回と比較できます。

```bash
python -X utf8 cognitag_struct/eval/run_eval.py --compare cognitag_struct/eval/baseline.json
```

退行（前回通っていたケースが落ちる）があれば終了コード 1 を返します。

## この点数の読み方

**絶対的な品質ではありません。** ケースは自作なので、自分に都合の良い問題を集めれば
いくらでも上がります。**変更前と変更後の比較にのみ意味があります。**

そして、主目的は点数を上げることではなく **退行を見つけること**です。
辞書を 1 つ足すと、狙った入力は良くなり、狙っていない入力が壊れます。
狙った改善は確認しなくても分かりますが、巻き添えの破損は探さないと見つかりません。
`--compare` の「新たに落ちたケース」が、この道具の一番重要な出力です。

## ケースの書き方

`cases.jsonl` に 1 行 1 ケース。`expect` は**最後のターン**に対する期待値です。

```json
{"id": "move_01", "turns": ["行きます"], "expect": {"tags_all": ["#移動"], "question_contains": "どこ"}}
{"id": "move_02", "turns": ["行きます", "名古屋"], "expect": {"policy_prefix": "answered", "text_contains": "名古屋に行きます"}}
```

書ける期待値は次の 10 種類です。ここに無いキーを書くとエラーになります
（綴りを間違えた期待値を黙って無視すると、検証しているつもりで検証されていない
状態が生まれるため）。

| キー | 意味 |
|---|---|
| `modality` | 発話の種類（`STATEMENT` `Q_OPEN` など 8 種） |
| `parsed` | 構造が取れたか（真偽） |
| `tags_all` | このタグが全部付いていること |
| `tags_none` | このタグが 1 つも付いていないこと |
| `question_contains` | **返答として**問い返し、その中にこの語が含まれること |
| `no_question` | 問い返さないこと（真偽） |
| `policy` | 応答方針の完全一致 |
| `policy_prefix` | 応答方針の前方一致（`answered*` をまとめる用） |
| `text_contains` | 返答にこの語が含まれること |
| `text_none` | 返答にこの語が含まれないこと |

`question_contains` と `no_question` が見るのは**返答**であって解析結果ではありません。
「行きますか」の解析には「どこに？」が入りますが、Responder は問いに問いで返さないので、
利用者には届いていません。届いたものを測ります。

### 期待値は「こうあるべき」で書く

現状の出力を写してはいけません。写すと、何を直すべきかが評価セットから消えます。
実装がまだ追いついていないケースは、落ちたままにして `note` に原因を書きます。

```json
{"id": "spec_05", "turns": ["壊れたみたいだ"], "expect": {"modality": "SPECULATION"},
 "note": "現状は落ちる。Sudachi が「みたい」と「だ」に割るので…"}
```

### `known_gap`

「今はまだ無理だが、次の段階で解消したい」ケースには `known_gap: true` を付けます。
点数には含めず、別枠で「何件中何件が解消したか」を数えます。

点数に混ぜないのは、**既知の弱点を評価セットから消すだけで点数が上がってしまう**のを
防ぐためです。別枠にしておけば、弱点が消えたことも記録として残ります。

`known_gap` には `note` が必須です（理由の書いていない弱点は、後から見て
直すべきか判断できないため）。

## いま落ちているもの

### 実装の弱点（点数に含む・3 件）

| ケース | 入力 | 原因 |
|---|---|---|
| `spec_05` | 壊れたみたいだ | Sudachi が「みたい」と「だ」に割るので、`HEARSAY_LEMMAS` の「みたいだ」に一致しない |
| `emo_06` | 不安です | 「不安」は名詞なので述語として数えられず `Unparsable`。`frames.jsonl` には登録済みなのに引かれない |
| `know_01` | 東京の人口は何人ですか | Sudachi が「何人です」を 1 語にするため疑問詞「何」が見えず、`Q_YESNO` と判定される |

3 件とも形態素解析の切れ方に起因していて、規則側の 1 行では直りません。

### 既知の弱点（別枠・8 件）

6 件は名詞の意味タグが取れないもの（`病院に行きます` から `#場所` が出ない等）で、
語彙辞書の接続で解消する見込みです。残り 2 件は訂正の受け取りと、
知識を要する依頼の判別です。

## 仕組み

- `CogniTag`（辞書と Sudachi）は 1 回だけ作って使い回します。重いので
- `Responder` は**ケースごとに作り直します**。文脈が残ると、前のケースの質問に
  次のケースの入力が答えてしまい、単独では再現しない結果になります
- プロダクトコードは 1 行も変更していません。測定のために観測点を本体へ足すと、
  測るための仕組みが測られる対象を変えてしまうためです
- `baseline.json` に時刻は書きません。2 回走らせれば完全に一致します
  （差分が時刻だけで出ると、退行の検出という主目的が埋もれるため）
